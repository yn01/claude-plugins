# dev-gate

A Claude Code plugin that defines machine-verifiable completion criteria for tasks and automatically runs verification commands to determine pass/fail.

dev-gate eliminates the ambiguity of "done." Instead of telling an agent what done looks like in prose, you encode it as executable commands. The agent runs them. The gate either passes or it doesn't.

## The Problem

When you ask an AI agent to "implement authentication," what does done mean? Tests passing? Coverage above 85%? The API returning 200? If you describe this in natural language, the agent may forget it, misinterpret it, or quietly skip it.

dev-gate solves this by storing completion criteria as structured Markdown files with embedded verification commands. Every criterion must be machine-checkable. Ambiguous criteria cannot be added.

## Relationship to dev-guide

dev-gate is a sister plugin to [dev-guide](../dev-guide/). They share the same design philosophy but serve different roles:

| Plugin | Role |
|--------|------|
| **dev-guide** | Delivers human-authored guidelines and decisions to the agent ("how to build it") |
| **dev-gate** | Verifies the agent's output against human-defined completion criteria ("is it done?") |

The two plugins are fully independent — no dependency between them. Each can be used alone.

## Design Philosophy: Human as Architect

dev-gate is a **gate**, not a generator.

- Completion criteria are written by humans, not auto-generated by AI
- Humans define what "done" means; the agent executes and is verified against that definition
- This keeps quality authority with the team

## Quick Start

```bash
# 1. Define a gate for a task you're about to work on
/dev-gate:define "Implement JWT Authentication"

# 2. Open the generated file and fill in completion criteria
# .dev-gate/active/GATE-20260529-143022-implement-jwt-authentication.md

# 3. Complete the task, then verify
/dev-gate:verify GATE-20260529-143022

# 4. If all criteria pass, the gate is archived automatically
# If any fail, fix the issues and verify again
```

## Commands

### `/dev-gate:define "<task title>"`

Create a new gate definition file in `.dev-gate/active/`.

The command generates a Gate ID (`GATE-YYYYMMDD-HHMMSS`), copies the gate template, and updates `index.md`. Open the generated file and fill in the completion criteria — each criterion must include a verification command.

```bash
/dev-gate:define "Implement JWT Authentication"
/dev-gate:define "Add User Registration API"
/dev-gate:define "Migrate users table to new schema"
```

### `/dev-gate:verify [gate-id]`

Run all verification commands in a gate and record the results.

- Each criterion's bash command is executed with a 60-second timeout
- Results are written to the `## Verification Results` table in the gate file
- All pass → status set to `passed`, file moved to `.dev-gate/archive/`
- Any fail → status set to `failed`, file kept in `.dev-gate/active/`
- Omit `gate-id` to verify all active gates

```bash
/dev-gate:verify GATE-20260529-143022   # specific gate
/dev-gate:verify                         # all active gates
```

### `/dev-gate:list [status]`

List gate definitions. Defaults to `open` if status is omitted.

| status | shows |
|--------|-------|
| `open` | gates awaiting verification |
| `passed` | gates that passed verification |
| `failed` | gates with failing criteria |
| `all` | all gates |

```bash
/dev-gate:list
/dev-gate:list all
/dev-gate:list passed
```

### `/dev-gate:template [keyword]`

Search archived (passed) gates for criteria to reuse in a new gate.

When you're defining a new gate for a task similar to a previous one, use this command to find relevant criteria you've already verified — and copy them into the new gate file.

```bash
/dev-gate:template                    # list all archived gates
/dev-gate:template "authentication"   # filter by keyword
```

## Gate Definition Format

Each gate is a Markdown file with this structure:

```markdown
# [Task Title]

## Gate ID

GATE-YYYYMMDD-HHMMSS

## Status

open / passed / failed

## Task Description

[What is being built?]

## Completion Criteria

### Criterion 1: [Description]

\`\`\`bash
npm test -- --grep "auth"
\`\`\`

Expected: exit code 0

### Criterion 2: [Description]

\`\`\`bash
npx c8 report --check-coverage --lines 85
\`\`\`

Expected: exit code 0

### Criterion 3: [Description]

\`\`\`bash
curl -s -o /dev/null -w '%{http_code}' http://localhost:3000/api/auth/login
\`\`\`

Expected: stdout contains "200"

## Verification Results

| Criterion | Result | Output |
|---|---|---|
| 1 | - | - |
| 2 | - | - |
| 3 | - | - |

## Notes

[Optional context]
```

**Rules:**
- Every criterion must include a bash verification command — no command, no criterion
- Success is defined as exit code 0, or stdout containing a specified string
- This structural requirement eliminates ambiguous "done" definitions


### Project directory (generated by `/dev-gate:define`)

```
.dev-gate/
├── active/              # Gates awaiting verification
│   └── GATE-YYYYMMDD-HHMMSS-<title>.md
├── archive/             # Gates that passed — reusable as templates
│   └── GATE-YYYYMMDD-HHMMSS-<title>.md
└── index.md             # Catalogue of all gates (auto-updated)
```

Commit `.dev-gate/` to your repository to share gate definitions and history with your team.

## Template Reuse

Verified (archived) gates accumulate over time into a library of proven completion criteria. Use `/dev-gate:template` to browse and reuse them when defining gates for similar tasks.

This makes quality standards portable across tasks: a test coverage criterion that worked for one API endpoint can be copied directly into the gate for the next one.

## Pre-commit Hook (Optional)

The `PreToolUse` hook watches for `git commit` commands. If any gates in `.dev-gate/active/` have `open` status, it prints a warning before the commit proceeds:

```
⚠️  dev-gate: 1 open gate(s) found. Run /dev-gate:verify to check completion criteria.
```

The commit is not blocked — this is advisory only.
