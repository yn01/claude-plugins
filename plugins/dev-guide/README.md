# dev-guide

A Claude Code plugin that stores human-authored technical guidelines, design decisions, and project concepts — and automatically injects relevant knowledge into the agent's context at session start.

dev-guide is an extended CLAUDE.md. CLAUDE.md works well for small projects, but grows unwieldy as a project scales. dev-guide solves this by splitting knowledge into topic-focused pages and injecting only the catalogue at session start. The agent fetches individual pages on demand.

## The Problem

`CLAUDE.md` is the standard place to document project rules and conventions, but it has a hard constraint: everything you put there is loaded into every conversation, whether relevant or not. At 100–300 lines this is fine. At 1,000+ lines it bloats the context window and buries important signals in noise.

dev-guide separates *storing* knowledge from *loading* it. You write as much as you need. The agent reads only what the current task requires.

## Design Philosophy: Human as Architect

dev-guide is a **pipe**, not a generator.

- Content is written by humans, not auto-generated by AI
- Humans define guidelines, record design decisions, and explain concepts
- The agent's role is to receive and apply that knowledge — not to create it

This keeps architectural authority with the team. The agent executes; the human architects.

## Installation

```
/plugin marketplace add yn01/claude-plugins
/plugin install dev-guide
```

## Quick Start

```bash
# 1. Add your first guideline
/dev-guide:add guideline "API Design Rules"

# 2. Open the generated file and fill in the content
# .dev-guide/guidelines/api-design-rules.md

# 3. On the next session start, the index is automatically injected
# 4. Query it anytime
/dev-guide:query "How should we design REST endpoints?"
```

## Commands

### `/dev-guide:add <category> "<title>"`

Add a new knowledge page to the project's `.dev-guide/` directory.

| Argument | Values |
|----------|--------|
| `category` | `guideline`, `decision`, `concept` |
| `title` | Short descriptive title |

The command copies the appropriate template, generates a filename from the title, and updates `index.md`.

For `decision` pages, ADR numbering (`ADR-001`, `ADR-002`, ...) is applied automatically.

```bash
/dev-guide:add guideline "Error Handling Policy"
/dev-guide:add decision "Use PostgreSQL over MongoDB"
/dev-guide:add concept "Tenant"
```

### `/dev-guide:list [category]`

List all registered knowledge pages. Omit `category` to show all.

```bash
/dev-guide:list
/dev-guide:list decision
```

### `/dev-guide:query <question>`

Search the knowledge base with a natural language question. Returns full page content for every relevant match.

```bash
/dev-guide:query "How should we handle database migrations?"
/dev-guide:query "What auth strategy do we use?"
```

### `/dev-guide:inject <topic>`

Manually inject pages related to a topic into the current context. Use this when the session-start injection didn't include something you need right now.

```bash
/dev-guide:inject "authentication"
/dev-guide:inject "error handling"
```

### Project directory (generated by `/dev-guide:add`)

```
.dev-guide/
├── guidelines/      # Coding conventions and technical policies
├── decisions/       # Architecture Decision Records (ADR format)
├── concepts/        # Project-specific terms and domain concepts
└── index.md         # Catalogue of all pages (auto-updated)
```

Commit `.dev-guide/` to your repository to share the knowledge base with your team.

## Automatic Injection

The `SessionStart` hook checks for `.dev-guide/index.md` in the current directory. If found, it prints the catalogue into the agent's context with a reminder to use `/dev-guide:query` or `/dev-guide:inject` for full page content.

Only the catalogue is injected — never all pages at once. This keeps the context window lean while making the agent aware of what knowledge exists.

## Templates

### Guideline (`templates/guideline.md`)

Structured as: **Scope → Rules → Examples (Do / Don't) → Rationale**

Use for coding conventions, architectural policies, and quality standards.

### Decision (`templates/decision.md`)

ADR format based on PMBOK 8th edition decision record structure: **Context → Decision → Consequences → Alternatives Considered**

Use to record why a significant technical choice was made. The "Context" and "Alternatives Considered" sections are especially important — they give the agent the reasoning behind the decision, not just the outcome.

### Concept (`templates/concept.md`)

Structured as: **Definition → Usage in this project → Related**

Use to define domain terms, project-specific abstractions, or concepts that are used differently here than in the wider industry.
